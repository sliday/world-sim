## Method

- Browser: Playwright 1.58 driving system Chrome 155 headless with GPU raster (ANGLE Metal on an Apple M4 Max). Desktop: 1440x900 at device scale 2 (canvas 2880x1800). Phone: 390x844 at device scale 3, touch, and a 4x CPU throttle to stand in for a mid-range phone (the renderer caps pixel density at 2, so the canvas is 780x1688).
- Each run: load the page, wait for the first live frame, then 30 s of frame timing and long tasks with no tracing, then a 12 s Chrome trace (main-thread split, thread CPU time per frame), then a 12 s CPU profile, then heap after GC. An init script wraps `JSON.parse` and the socket `message` listener to time each snapshot, and hooks the first `drawImage` of the map layer to time the first map paint.
- HEAT off and HEAT on (`stigmergy:heat-view` = `faint` / `strong`) for both viewports.
- Live numbers come from production at tick 401,300 (100 agents, 140 artifacts).
- Local numbers come from a replay harness (`node` + `ws`, permessage-deflate like production) that serves a build and replays 10 consecutive production frames (ticks 401,318 to 401,327) every 10 s. BEFORE serves the `efa7970` build with full frames; AFTER serves this branch with the Worker's frame encoder. Both serve the same captured data.
- The machine is shared with other agents. Load average swung from 5 to 57 during the run. I ran three interleaved BEFORE/AFTER repetitions; rep 3 ran at load 7 to 13 and is the table below. Reps 1 and 2 (load 5 to 57) point the same way: desktop CPU per frame 8.7 to 11.0 ms before against 3.0 to 5.0 ms after. Draw-call counts and the engine comparison do not depend on load.

## Bottlenecks and fixes, most impactful first

### 1. p5's Friendly Error System checked every drawing call

Evidence: zod schema parsing plus the validator wrapper took about 22% of main-thread time on both viewports. The full `p5` entry also pulls in WebGL, the shader transpiler with `escodegen`, `acorn`, `i18next`, DOM helpers and data/IO modules, which make up most of the 1.25 MB bundle.

Fix (`src/sim/renderer.ts`, `src/p5-modules.d.ts`): import `p5/core` and register only the modules the sketch calls (shape, accessibility, color, events, image, math, utilities, type) in the order the full build registers them. The Friendly Error System no longer loads, so its checks and its source re-fetch are gone. `p5/core` needs the accessibility module because `resizeCanvas` calls into it. p5 ships no types for these entry points, so a small declaration file maps `p5/core` to the full build's types.

Impact: main bundle 1,251 KB to 618 KB (brotli 295 KB to 157 KB), evaluate time on the throttled phone 167 ms to 110 ms, first map paint on emulated slow 4G 3.3 s to 2.3 s, and the validator's 22% share of every frame.

### 2. Entities drew far outside the view

Evidence: `visibleCopies` drew any wrapped copy within a whole viewport width and height of the camera, an area four times the screen. On desktop the window (2880x1800 world px) is larger than the map (1536x1152), so most entities drew two or three times. `drawInfiniteMap` blitted a 4x4 grid of map copies (16 `drawImage` calls) where one to four are visible.

Fix (`src/sim/renderer.ts`): each caller passes a reach, the farthest its drawing extends from its anchor (stations 16, artifacts 24, event ring 32, agents `24 + 32 / zoom` because their icon scales against zoom, trail segments their own length plus 4). A copy draws when it lies within half the view plus that reach. Speech bubbles keep the old window because they clamp to the screen edge. The map loop blits only copies that overlap the view plus one pixel of slack.

Impact: `fill` calls per frame dropped 63% on desktop, `fillText` 66%, `drawImage` from 20 to 2. Together with fix 1, this accounts for the per-frame gain in the tables above.

### 3. Trail lines paid for a fill with no area

Evidence: p5's `drawShape` calls `ctx.fill(path)` whenever a fill color is set, and the trails ran with the atmosphere's fill still set, so every trail segment issued a native `fill` of a zero-area line.

Fix: `p.noFill()` once before the trails. Every later draw sets its own fill, and screenshots confirm identical pixels.

### 4. Every socket frame resent the whole terrain

Evidence: terrain is 726 KB of a 1.22 MB snapshot (59%) and 157 KB of its 215 KB deflated size (73%), because its tile values are full-precision floats. One tick changes about 300 of 6,912 tiles (the environment pass updates every 23rd tile, plus harvested and artifact tiles). The renderer reads terrain only when it builds its terrain layer.

Fix (`src/sim/snapshot-stream.ts`, `worker/index.ts`, `src/sim/client.ts`): the Worker keeps the terrain it last broadcast and sends `terrainPatch: { fromTick, tiles: [index, tile][] }` with complete new values for each changed tile. Terrain changes only inside `advanceWorld`, which also advances the tick, so the tick names the terrain a client holds. The client applies a patch when it holds `fromTick`, keeps its terrain when it already holds the frame's tick (it connected while that tick was broadcasting), and otherwise reloads `/api/snapshot`. The socket's first frame, `/api/snapshot` and the browser fallback still carry full snapshots. After an eviction the Worker has no base and sends a full frame.

Impact: frames go from 1.24 MB to 552 KB raw and from 218 KB to 70 KB deflated; parse time drops by about 40% on both viewports; the Worker's `JSON.stringify` per broadcast drops from about 2.6 ms to 1.1 ms (Node, same frames), and the diff costs 0.1 to 0.3 ms. Decoding every captured production frame against its predecessor reproduces the original frame exactly (`isDeepStrictEqual`).

### 5. The client re-downloaded the full snapshot every 15 s

Evidence: the 15 s poll fetched `/api/snapshot` (228 KB zstd, 1.2 MB parse) even with a healthy socket, and a poll could land a tick behind the socket and send gliding bots backward for a moment.

Fix (`src/sim/client.ts`): the poll skips while the socket is open and delivered a frame in the last 25 s. A closed or silent socket still falls back to polling.

Impact: with the terrain patches, snapshot traffic per open tab falls from about 133 MB per hour (78 MB socket plus 55 MB polling) to about 25 MB. Verified in a browser: one dropped frame triggered one reload and the patches resumed; a silent socket resumed polling at 30 s and 45 s.

### 6. The world kept drawing under full-page views

Evidence: with About or the Craft Tree open, the opaque overlay hides the canvas while p5 keeps drawing 60 frames a second.

Fix (`src/main.ts`, `src/sim/renderer.ts`): 240 ms after one of those pages opens (its fade takes 220 ms), the renderer skips its draw body; it resumes as soon as both close. The p5 loop keeps ticking, so there is no `noLoop`/`loop` restart race and the first frame after closing eases on from where it stopped.

Impact: main-thread task time with About open fell from 878 ms/s to 6 ms/s on desktop.

### 7. Engine: `resourcePosition` scanned 1,728 tiles per call

Evidence: on the live world, `advanceWorld` costs 1.53 ms per tick in Node; the drained-shore test spent most of its 2,000 ticks inside this scan.

Fix (`src/sim/engine.ts`, `src/sim/types.ts`): tile kinds never change after `createTerrain`, so a `WeakMap` keyed by the terrain array groups the sampled tiles by material once, in the original y-then-x order. Each search visits only its material's tiles with the same arithmetic and the same strict comparisons, so ties resolve the same way. The function returns a copy of the chosen point. `Tile.terrain` is now `readonly`, so the compiler rejects any future write that would invalidate the index.

Proof of identical results: I bundled the engine from `efa7970` and from this branch and ran the same scenarios. 300 ticks from the captured tick-401,327 state produce byte-identical `publicSnapshot` JSON (SHA-256 `587f83d2...`). 3,000 ticks of a fresh world give the same state hash (`2bf32195...`), and so do 2,000 ticks of the drained-shore scenario (`10f24993...`). The existing replay and determinism tests pass.

Impact: live-world tick 1.53 ms to 0.43 ms; drained-shore scenario 2,232 ms to 556 ms. The drained-shore test now runs in about 1 s and has a 60 s timeout for loaded machines (it had 20 s and took about 18 s under load).

## Visual check

Method: a fake clock replaces `performance.now` and `requestAnimationFrame`, both builds load the same frozen snapshot, and the script steps the same frames: 240 frames at the default camera, zoom fully out, zoom fully in, drag, window resize, select an agent and follow it. I compare the canvas backing store (`toDataURL`) pixel by pixel. The old client re-polls every 15 s of wall time and re-targets gliding bots, so the script serves `/api/snapshot` once to keep both builds on the same inputs.

Result: across desktop heat off, desktop heat on and phone, every state matches except up to 4 pixels with a channel difference of 1, the same GPU noise two BEFORE runs show against each other. One phone run differed in the screen-space dust and the event ring only: a resize event landed on a different frame, which shifts `frameCount`; agents, trails and terrain matched. Full-page screenshots also differ by about 170 pixels in the glass panels between two BEFORE runs, so I compared the canvas itself.

## Considered and rejected

- Code-splitting the craft tree: its modules weigh about 10 KB of a 618 KB bundle, so a split would not move first paint.
- Pre-rendering bots and artifacts into sprites: they draw at fractional device positions under a continuous zoom, so a cached bitmap resamples and changes pixels.
- Drawing glyphs or shapes through the raw 2D context instead of p5: p5's vertical text centering and path building would have to be copied exactly; the remaining gain did not justify the risk to pixel identity.
- Rounding terrain floats or quantizing the snapshot: it changes the authoritative data.
- Delta-encoding agents and artifacts: they are most of the remaining 552 KB (agents 330 KB, artifacts 128 KB), but every agent changes every tick, so it needs a field-level diff design. Worth a follow-up.
- Dropping the duplicate initial load (HTTP snapshot plus the socket's first full frame): the HTTP fetch detects an unavailable API for the fallback and the socket frame seeds the patch base; merging them changes the connection protocol.
- Speeding up the terrain-layer build (about 25,000 p5 calls, 50 ms desktop, 200 ms throttled phone at setup): it runs once, and replacing p5 calls risks pixel changes in the base map.
- Lowering the canvas pixel density cap of 2: it would blur the map on high-density screens.
- Pausing p5 with `noLoop()`: calling `loop()` within one frame of `noLoop()` starts a second draw chain, so the pause skips the draw body instead.
